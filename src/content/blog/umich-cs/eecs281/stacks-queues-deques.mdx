## What are containers?

Containers are objects, classes, or a data structure that stores a collection of other objects/elements, and manages the operations and memory associated with them. 

There are a couple of different types of containers, and a couple of distilled data structure descriptions that correspond with them. You don't necessarily need to know what all of these are, just know that they exist & that they will be revisited.

#### 1. Sequence Containers (Linear Data Structures)
Sequence containers, as the name implies, stores data in a linear pattern such that all of the elements can be accessed sequentially. Examples:

- **Arrays**: A fixed-sized contiguous block of memory.
- **Vectors**: A resizable array.
- **Linked Lists**: A chain of nodes containing data and pointers to the next [and/or previous] node. 
- **Deques**: Fast insertions and deletions at the front & back of the data structure.

#### 2. Ordered Associative Containers (Sorted/Key-Based)
Associative containers store data in *some* sorted order. They usually provide fast search, insertion, & deletion in O(log n) time. Usually, associative containers are implemented as balanced binary search trees, most commonly Red-Black trees. Examples:

- **Sets**: Collection of unique elements sorted by their values.
- **Multiset**: Same thing as a set, but allows multiple copies of the same value
- **Maps**: Collection of key-value pairs sorted in which no two pairs have the same key.
- **Multimap**: Same thing as a map except that multiple pairs can have the same keys.

#### 3. Unordered Associative Containers (Hashed)

Unordered associative containers implement unsorted hashed data structures that can be searched quickly. I.e. O(1) amortized, and O(n) worst case. Examples:

- **Unordered Set**: Collection of unique elements hashed by their values.
- **Unordered Map**: Collection of key-value pairs that are hashed by their keys, where no two pairs have the same key. 

And the same goes for unordered multisets & multimaps: their implementation uses hashing instead of trees to organize their data.

Most of these definitions come directly from [GeeksForGeeks article on containers](https://www.geeksforgeeks.org/cpp/containers-cpp-stl/)


## Briefly: Container Adapters (Restricted Interfaces)
Container adapters are wrappers around one of the sequence containers above that hide most of its interface and expose only the operations that make sense for a particular abstract data type. Importantly, stacks and queues are **NOT** sequence containers, but rather container adapters for a deque. For example, a stack is just a sequence where you're only allowed to touch one end. 

This makes a bit more sense when you actually look at a stripped down implementation for a `std::stack`:

```cpp
template<class T, class Container = std::deque<T>>
class stack {
    Container c;   // the ONLY data member

    public:
        void push(const T& x) { c.push_back(x); }
        void pop()            { c.pop_back(); }
        T& top()              { return c.back(); }
        bool empty() const    { return c.empty(); }
        size_t size() const   { return c.size(); }
    };
```

You can see it's literally just a deque wrapped up and called a stack, and the stack class only exposes the methods it wants you to use (push, pop, top, empty, size)

The STL has three container adapters: `std::stack`, `std::queue`, and `std::priority_queue`. C++23 added `std::flat_map`/`std::flat_set` and their multi variants, which adapt a sorted vector into a map/set interface.

The key idea: the ADT (what operations exist) is separated from the implementation (how the data is actually laid out). You pick the underlying container; the adapter supplies the interface.


## Stacks

A stack operates under the "Last in, first out" (LIFO) rule. The traditional analogy is "a stack of plates" (i.e. you take a plate from the top, not generally the middle). A couple of other examples include web browser's "back" feature and the undo buttons in text editors.

The ADT for stacks is the following:

| Operation           | Description                                                     |
|---------------------|-----------------------------------------------------------------|
| `push(x) → void`    | Adds `x` to the top of the stack                                |
| `pop() → void`      | Removes the top element; requires stack not empty               |
| `element &top() → T`| Returns a reference to the top element; requires not empty      |
| `isEmpty() → bool`  | True if the stack has no elements                               |
| `size() → int`      | Number of elements                                              |

### Implementations

Stacks are, by default, implemented with a `std::deque` (we'll come back deques later). However, you can also pass in `std::list` (i.e. the STL's doubly linked list), or `std::vector` (among others, also to be covered later.)

If we were to implement a stack ourselves, our complexity analysis would look something like this table:

| Method | Array/Vector | Linked List | Deque (STL default) |
|---|---|---|---|
| `push(element)` | Constant (linear when resizing vector)* | Constant | Constant |
| `pop()` | Constant | Constant | Constant |
| `element &top()` | Constant | Constant | Constant |
| `size()` | Constant | Constant (with tracked size) | Constant |
| `empty()` | Constant | Constant | Constant |

\*Averages out to constant with many pushes (amortized constant)

Keep in mind that linked lists will usually have higher memory overhead, so they're not usually ideal. 

## Queues

Queues operate under the "First in, First out" (FIFO) principle. This is simple. If you're the first in line, then you're the first person "to be dealt with" (First item added, first one removed). Common examples are office hour queues, a fast food drive-through, or printer spooling (remember waiting for that dickhead to print 85 pages 3 minutes before your Lab starts? Your *single sheet of paper* was in the queue behind him.)

The ADT for queues is the following:

| Operation           | Description                                                     |
|---------------------|-----------------------------------------------------------------|
| `push(x) → void`      | Copy element to the back of the queue                         |
| `pop() → void`        | Removes element at the front of the queue                     |
| `element &front() → T`| Returns a reference to the element at the front of the queue; requires not empty |
| `isEmpty() → bool`    | True if the stack has no elements                             |
| `size() → int`        | Number of elements                                            |

## Implementations
At the University of Michigan, they showed an implementation of a circular (also called a **ring**) buffer that doubles when it fills up as a potential implementation for a queue. The usefulness of this example sort of runs out quickly because it produces neither a clean ring buffer nor a clean dynamic array, which makes it hard to learn the idioms of dynamic arrays AND circular buffers.

> **Fun Facts**: Real ring buffers are fixed-capacity. Being bounded to a fixed size is the whole point of a ring buffer. Growing an array by doubling the capacity & copying the contents to a new array is the 'dynamic-array' idiom.

In practice you’d reach for `std::deque` for a growable queue, and if you want to understand ring buffers, study the fixed-capacity version where the interesting question is what happens when it fills.
